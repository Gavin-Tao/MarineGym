## 表 2. 为什么？—— 任务是能力受限，不是信息受限

下列数值全部来自**训练后策略的实测轨迹**（`fig5_traj`，600 步 × 16 env，
由 checkpoint 回放采集），非估算：

| 量 | 实测值 | 说明 |
|---|---:|---|
| 参考点速度 | **0.543 m/s** | `d(target_pos)/dt` |
| 载具实际速度 | **0.279 m/s** | `d(pos)/dt` |
| **速度达成率** | **51%** | 载具只跑出参考速度的一半 |
| 速度亏空 | 0.263 m/s | 参考 − 实际 |
| 跟踪误差增长率 | **0.413 m/s** | 对误差-时间曲线线性拟合 |
| 终止阈值 | 0.5 m | `Track.yaml: reset_thres` |
| **由误差增长率反推的 episode 长度** | **76 步** | 0.5 / 0.413 / dt |
| 实测 episode 长度（轨迹回放，中位数） | 67 步 | |
| 实测 episode 长度（正式评测，均值） | 57.86 步 | 表 1 |

> 载具只能达到参考速度的 51%，
> 跟踪误差因而以约 0.41 m/s **线性增长**（见 `fig5_traj` 面板 b，
> 拟合直线与实测曲线几乎重合），撞上 0.5 m 阈值的时刻由**运动学**决定，
> 与策略、观测信息、网络架构无关。这解释了表 1 中全部条目为何一致到小数点后第三位。
>
> **推论：原始 Track 配置不能用于比较策略架构。** 必须先把参考速度降到载具能力之内，
> 让任务从"必然失败"变成"可持续跟踪"，跟踪精度才会成为有区分度的指标。
